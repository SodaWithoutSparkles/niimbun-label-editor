# i18n

`react-i18next` + `i18next` (string-key `t()` API; i18next 26.x ships `enableSelector: false`).
`en` only; a second locale is a one-line catalog + one `languageOptions` entry.

## Shape (load-bearing)

- Catalog `src/i18n/locales/en.json` is **bare-key** — the object at top level, not wrapped in a `translation` key. `tsconfig` has `resolveJsonModule` on for this.
- Init `src/i18n/index.ts` nests it as `resources: { en: { translation: en } }`. Wrong shape → `t()` echoes raw keys instead of translating.
- `interpolation.escapeValue: false` (React renders text, never `innerHTML`). `react.useSuspense: false`. `fallbackLng: 'en'`.

## Typed keys

- `src/@types/i18next.d.ts` augments `CustomTypeOptions` with `resources: { translation: typeof en }` and `defaultNS: 'translation'`. `include: ["src"]` picks it up.
- The file **must be a module** (top-level `import`) or `declare module` becomes an ambient override that silently does nothing.
- `import type en from '.../en.json'` is required (`verbatimModuleSyntax`).
- Result: a bad literal key is a `tsc` error, and editor autocomplete works. Prove it by temporarily inserting a bogus key — `tsc` must fail.
- **Never annotate a parameter with the whole generic `t` type** (`ReturnType<typeof useTranslation>['t']`). Materialising that type is instantiation-depth-sensitive: adding **unrelated** i18n keys/usage elsewhere can then fail `tsc` in *that* file with `TS2589` (excessively deep) and a bogus `TS2322`. Close over `t` in a small hook instead (e.g. `useWarningText()` returning `(warning) => string`), so no signature names the generic. Incident: `WarningsTab.tsx` `warningText` (P15, 2026-10-19).

## Dynamic keys — the literal map

Typed keys come from the JSON literal tree, so a computed key like `t('tools.' + id)` **will not typecheck** (it collapses the union to `string`). Use an `as const` map from the runtime value to a literal key:

```ts
export const TOOL_LABEL_KEYS = { select: 'tools.select', /* … */ } as const
// then: t(TOOL_LABEL_KEYS[id])
```

`src/components/layout/toolLabels.ts` is the canonical example. Do **not** widen `CustomTypeOptions` to escape the union.

## History labels: store keys, render at the edge

`HistoryEntry` (`src/types.ts`) is `{ key: string; params?: Record<string, unknown> } | string`. Slices store the **key + params**, not rendered text; `RightSidebar` renders via `t(key, params)`.
- The `| string` arm exists so **pre-migration saved files** (history holds plain strings) still load — a string renders as-is, an object goes through `t()`. Never assume the object shape.
- Plural counts use `_one` / `_other` keys (`en.json` is otherwise flat single-form). `en` falls back to the base key if plurals are absent, but any locale keeping `{{count}}` keys needs `_one`/`_other`.

## Dev-only missing-key guard

`parseMissingKeyHandler` in `src/i18n/index.ts`, gated on `import.meta.env.DEV`. Returns `⟦missing:key⟧` and `console.warn`s once per key (dedupe via a `Set`). Absent from production builds.
- Rationale: typed keys cover literal call sites only; the guard catches dynamic keys and keys removed from the catalog while a non-literal reference still points at them. A dead catalog key is invisible to `tsc` either way, so grep before deleting one.

## Language wiring

Settings store's `language` is the source of truth. Applied twice:
1. At i18n init (`src/i18n/index.ts`) from `useStore.getState().language`.
2. A subscription-like effect in `Header.tsx` calls `i18n.changeLanguage(language)` when it changes (guarded against re-firing the init value).

`GeneralSection`'s language `Select` only calls `setLanguage` — it does not touch i18n directly.

## Out of scope by design

- Console messages, font-family names, file extensions, `px`/`%`/numeral readouts, glyphs (`✓`, `✕`), OS file-picker `description`, `index.html`'s `<title>` — data or static HTML, not rendered copy.
- `ErrorBoundary` is a class component → use `i18n.t()`, not the `useTranslation` hook.
- Don't pass `t` around as a bare function ref (future i18next selector-API migration).
